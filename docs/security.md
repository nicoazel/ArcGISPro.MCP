# Security and operational limits

The add-in is local automation running with the signed-in ArcGIS Pro user's authority. It is not a sandbox for hostile code or geoprocessing tools.

Status: development preview. The supported configuration is an interactive same-user workstation with dockpane approvals. Autonomous mode is an opt-in expert setting, not recommended.

- Named-pipe connections are restricted to the same Windows user. Each ArcGIS Pro process listens on its own per-PID pipe (`ArcGISProMCP.v1.<pid>`) and publishes a local discovery record; several concurrent Pro processes are supported (see the pipe limits below).
- Requests are versioned, correlated and limited to 8 MiB.
- Mutating operations require a current workspace revision. Revision checks are an optimistic guard, not a database transaction or a lock against all external edits.
- Workflows containing writes require a matching initial revision before any step executes; leading read-only steps cannot refresh stale authorization. Every subsequent write also checks the revision after acquiring the shared execution gate. Only a successful write step advances the expected revision, to the revision that write produced; read-only steps and failed steps (including `continueOnError` failures) never advance it, so they cannot adopt a change nobody reviewed.
- If the workspace revision changes mid-run (a person edits the project, or ArcGIS Pro publishes a delayed change), the next write step is rejected before it executes and the run stops with `workspace_changed`, reporting `stoppedAtStep`, `stepIndex`, `expectedRevision` and `currentRevision`. This happens even when the step sets `continueOnError`. The run is not retried against the newer revision, and completed steps are not rolled back. Refresh state, review, and start a new run.
- Registry invocations and workflows can use process-lifetime idempotency keys (maximum 2048 combined entries). Workflow idempotency keys require an immutable `version`. The cache is not durable across Pro restarts. Faulted requests remain cached because a write may have happened before the fault; operation approval rejection can be repeated with a newly approved token. Keys bind operation/workflow version, arguments and initial revision. A keyed request runs under the host's lifetime, so cancelling the first caller does not cancel work that a second caller with the same key is waiting on.
- In default mode, confirmation-gated operations fail closed without a short-lived, single-use token. These are every Destructive or ExternalSideEffect operation plus the SafeWrite operations `project.open`, `project.save` and `feature.update`. Request local review with `approval_request`, then poll `approval_status`. Only a person in the dockpane can approve/deny. Tokens bind the exact operation version, canonical arguments and workspace revision; consuming a token is atomic. `approval_cancel` revokes a pending/approved request. The old literal `interactive` token grants nothing.
- When a request will run user code (any `arcpy.*` run, a `gp.run` tool from a `.pyt`/`.atbx`/`.tbx` toolbox, or a `gp.run` parameter that selects a Python expression type or mentions `arcpy.`), the approval card shows a highlighted "Runs user code" warning, and a `gp.run` result carries a `user_code_execution` notice. Detection is a conservative label, not a sandbox: a request without the warning can still run Python.
- Dockpane buttons that trigger a confirmation-gated operation (for example **Open project**) treat the click as the approval. The panel requests an approval, approves it once, and invokes with that token through the same queue and executor as MCP requests, so the token stays bound to the exact arguments and revision and the decision is audited with actor `panel-action`. An unused panel token is cancelled.
- `ARCGIS_PRO_MCP_AUTONOMOUS_MODE=true` is an explicit host-startup override. It is an opt-in expert setting and is not recommended. It lets the connected same-user client bypass local review for generic geoprocessing (including the Python execution paths described below), metadata writes, feature deletion, ArcPy execution, and other risky operations. Current revisions, schemas, operation limits, idempotency, and audit still apply, and results carry an `autonomous_control` warning. Treat this setting as equivalent to granting the client the user's ArcGIS authority; never enable it for an untrusted client or shared pipe.
- **`gp.run` can execute arbitrary Python.** The generic geoprocessing runner accepts any toolbox-qualified tool name and runs it with the user's GIS authority. That includes Python toolboxes (`.pyt`) and script tools, and tools that evaluate Python, such as Calculate Field or Calculate Value with a Python expression. Arbitrary Python is therefore reachable through `gp.run` even when the optional ArcPy runner is disabled. `gp.run` is confirmation-gated: in default mode it runs only after a person approves the request in the dockpane, and the approval is bound to the exact arguments. Read the tool name and the arguments preview before approving. In autonomous mode there is no such gate. Use trusted toolbox names and disposable output paths, and do not expose this bridge to an untrusted client.
- Workflows reference registered operations and cannot embed a script step. This does not sandbox a geoprocessing tool's internals.
- Workflow operation allowlists are enforced when a workflow is saved and again when it runs. A workflow without `allowedOperations` may use any registered operation except those that execute user code (`gp.run`, `arcpy.run-script`). When `allowedOperations` is present it is exhaustive: every step's operation must be listed, and user-code operations must be listed explicitly. Violations are reported as the validation issue `operation_not_allowed`; `workflow_run` then fails with `invalid_workflow` before any step executes. Skill manifests must declare a non-empty `allowedOperations` or they are not loaded; a skill's list documents the operations its guidance relies on and is not a separate runtime gate.
- Workflows cannot execute confirmation-gated steps in default mode. `workflow_run` passes no approval token to its steps and there is no per-step approval yet, so a step such as `gp.run`, `metadata.update`, `feature.update`, `feature.delete`, `project.save` or `arcpy.run-script` fails with `confirmation_required`. In autonomous mode those steps run without review.
- Operation audit records are JSON lines in `%LOCALAPPDATA%\ArcGISProMCP\audit\operations.jsonl`. Each record has a `kind`: `operation` for every invocation, including rejected calls and unknown operation ids (logged with version `unknown` and error `operation_not_found`, id truncated to 256 characters), and `approval` for every local approve/deny decision, with `decision` (`approved`/`denied`) and `actor` (`panel-card` for a reviewed request, `panel-action` for a dockpane button). Operation records carry `autonomousBypass: true` when autonomous mode skipped review. Records store an argument hash, not the arguments. Approval expiry and `approval_cancel` are not audited. When the active file exceeds 16 MiB it is renamed to `operations.<utc-timestamp>.jsonl`; the newest five rotated files are kept and older ones deleted. An audit write failure does not hide an operation's known result; it adds an `audit_write_failed` notice.
- Captured images use opaque process-local handles, at most 5 MiB each. The host index retains at most 100 captures / 64 MiB, with a 24-hour TTL checked on access. Retention deletes only files owned by the current store, never arbitrary project files or historical demo exports. Physical deletion is best effort; orphan files from prior sessions or locked files are not automatically reclaimed. These are index bounds, not a cross-restart disk quota.
- GIS operation results can include source paths and project identifiers.
- Optional ArcPy execution is a trusted-local, arbitrary-code boundary. It is disabled unless explicitly configured, uses ArcGIS Pro's Python environment, and remains confirmation-gated with hash-pinned scripts plus bounded arguments, output, time, and working-directory controls. It is not an OS sandbox: an approved script has the signed-in user's file, network, ArcGIS, and licensing authority; deliberately detached child processes may outlive best-effort process-tree termination. See [ArcPy configuration](arcpy.md).

The pipe supports at most eight concurrent requests (including the listener slot), with ten-second frame I/O timeouts. Host operations are serialized; discovery, state and approval calls bypass that gate. A stalled peer cannot monopolize the listener. ArcGIS itself may still delay state capture while its UI/MCT is busy. Each process defaults to a per-PID pipe; the gateway auto-selects one discovered live host or requires `ARCGIS_PRO_MCP_HOST_PID`/`ARCGIS_PRO_MCP_PIPE` when several are present. Reusing one explicit pipe across hosts is unsupported.

After request transmission starts, a dropped connection or response timeout is reported as `outcome_unknown`, not automatically retryable. The accepted write may still complete. Cancellation is cooperative; short SDK writes drain rather than detach from the executor. Disconnecting the panel blocks queued/new operations, not an already accepted write.

Workflows hold the same execution gate for their entire run, preventing registry/panel operations from interleaving between steps. They are still not atomic against external user edits or failures. Failed required dependencies are skipped and a run with any failed/skipped step is recorded as failed even when `continueOnError` allows independent steps to proceed. There is no automatic rollback. Audit/history persistence failures preserve the known result and return a warning rather than masking an accepted mutation.

Before production distribution: sign packages, complete live approval/replacement/shutdown tests, add crash-recoverable job status, and validate licensing/data policies. This bridge is a trusted-local-client boundary, not isolation between applications running as the same Windows user.
