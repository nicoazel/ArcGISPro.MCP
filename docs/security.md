# Security and operational limits

The add-in is local automation running with the signed-in ArcGIS Pro user's authority. It is not a sandbox for hostile code or geoprocessing tools.

Status: development preview. The supported configuration is an interactive same-user workstation with dockpane approvals. Autonomous mode is an opt-in expert setting, not recommended.

- Named-pipe connections are restricted to the same Windows user. Each ArcGIS Pro process listens on its own per-PID pipe (`ArcGISProMCP.v1.<pid>`) and publishes a local discovery record; several concurrent Pro processes are supported (see the pipe limits below). The development FakeHost (`tools/ArcGISProMCP.FakeHost`, not shipped) serves a fake project on the same kind of pipe, so its record is marked `hostKind: fakehost` and its project name is prefixed `[FakeHost] `. Automatic host selection ignores FakeHost records: the gateway attaches to one only when `ARCGIS_PRO_MCP_HOST_PID` or `ARCGIS_PRO_MCP_PIPE` names it, or `ARCGIS_PRO_MCP_ALLOW_FAKEHOST=true` is set for that gateway process. FakeHost warns at startup when ArcGIS Pro is running. Any same-user process can still publish a record or pipe that claims to be ArcGIS Pro; the host kind is a guard against mistakes, not an authentication boundary.
- Requests are versioned, correlated and limited to 8 MiB.
- Mutating operations require a current workspace revision. Revision checks are an optimistic guard, not a database transaction or a lock against all external edits.
- Workflows containing writes require a matching initial revision before any step executes; leading read-only steps cannot refresh stale authorization. Every subsequent write also checks the revision after acquiring the shared execution gate. Only a successful write step advances the expected revision, to the revision that write produced; read-only steps and failed steps (including `continueOnError` failures) never advance it, so they cannot adopt a change nobody reviewed.
- If the workspace revision changes mid-run (a person edits the project, or ArcGIS Pro publishes a delayed change), the next write step is rejected before it executes and the run stops with `workspace_changed`, reporting `stoppedAtStep`, `stepIndex`, `expectedRevision` and `currentRevision`. This happens even when the step sets `continueOnError`. The run is not retried against the newer revision, and completed steps are not rolled back. Refresh state, review, and start a new run.
- Registry invocations and workflows can use process-lifetime idempotency keys (maximum 2048 combined entries). Workflow idempotency keys require an immutable `version`. The cache is not durable across Pro restarts. Faulted requests remain cached because a write may have happened before the fault; operation approval rejection can be repeated with a newly approved token. Keys bind operation/workflow version, arguments and initial revision. A keyed request runs under the host's lifetime, so cancelling the first caller does not cancel work that a second caller with the same key is waiting on. As a consequence, once keyed work has started no caller can cancel it: cancelling only stops that caller from waiting (`request_cancelled`), and the work still runs to completion, even while it is queued behind the execution gate and nobody is waiting any more. Only host shutdown cancels it, and waiting callers then receive `host_stopping`.
- In default mode, confirmation-gated operations fail closed without a short-lived, single-use token. These are every Destructive or ExternalSideEffect operation plus the SafeWrite operations `project.open`, `project.save` and `feature.update`. Request local review with `approval_request`, then call `approval_status`, optionally with `waitSeconds` (up to 120) to wait for the decision instead of polling; waiting never approves anything. Only a person in the dockpane can approve/deny. Tokens bind the exact operation version, canonical arguments and workspace revision; consuming a token is atomic. `approval_cancel` revokes a pending/approved request. The old literal `interactive` token grants nothing.
- When a request will run user code (any `arcpy.*` run, a `gp.run` tool from a `.pyt`/`.atbx`/`.tbx` toolbox, a `gp.run` of Calculate Field, Calculate Fields or Calculate Value in any naming form such as `management.CalculateField` or `CalculateField_management`, or a `gp.run` parameter that selects a Python expression type or mentions `arcpy.`), the approval card shows a highlighted "Runs user code" warning, and a `gp.run` result carries a `user_code_execution` notice. The calculate tools are flagged regardless of their parameters because ArcGIS Pro defaults their expression type to Python 3. Detection is a conservative label, not a sandbox: a request without the warning can still run Python. A known false negative is a Python toolbox that was imported earlier (for example with `arcpy.ImportToolbox`) and is then called by its alias, such as `mytools.MyTool`; the tool name carries no `.pyt` path, so no warning is shown.
- MCP elicitation is deliberately not used for approvals. An elicitation prompt is rendered by the MCP client, so the client UI, which is the party asking for the risky call, would become the approval authority; the approval must stay in the ArcGIS Pro dockpane, outside the client's control. Many clients also do not support elicitation. URL-mode elicitation that only points a person at the dockpane decision may be added later.
- `registry_invoke` with `dryRun: true` never executes the operation, skips the revision and approval gates, and neither queues a review nor validates or consumes a token. It cannot be combined with an idempotency key. A dry run's verdict (for example `gp.run`'s `wouldBeRefused` or `approvalWarning`) is advisory and grants nothing.
- Dockpane buttons that trigger a confirmation-gated operation (for example **Open project**) treat the click as the approval. The panel requests an approval, approves it once, and invokes with that token through the same queue and executor as MCP requests, so the token stays bound to the exact arguments and revision and the decision is audited with actor `panel-action`. The click always creates its own approval request; it never reuses, and so never approves, an identical pending request queued by an MCP client, which stays pending for its own review. An unused panel token is cancelled.
- `ARCGIS_PRO_MCP_AUTONOMOUS_MODE=true` is an explicit host-startup override. It is an opt-in expert setting and is not recommended. It lets the connected same-user client bypass local review for generic geoprocessing (except the Destructive and UserCode tools described below), metadata writes, feature deletion, ArcPy execution, and other risky operations. Current revisions, schemas, operation limits, idempotency, and audit still apply, and results carry an `autonomous_control` warning. Treat this setting as equivalent to granting the client the user's ArcGIS authority; never enable it for an untrusted client or shared pipe.
- In autonomous mode `gp.run` still refuses tools whose [risk tier](#geoprocessing-risk-tiers) is Destructive or UserCode, tools it cannot classify, and any request the user-code detector flags, with `destructive_tool_requires_review` before anything executes. The refusal applies only to requests without a confirmation token: the dockpane approval queue keeps working in autonomous mode, so the client can request local review with `approval_request`, wait for a person to approve it in the dockpane, and retry with the token. A request that carries a token is validated exactly as in default mode (bound to the operation, arguments and revision, single use) and is audited with `autonomousBypass: false`; an invalid or expired token fails with `confirmation_required` and never falls back to the autonomous bypass.
- **`gp.run` can execute arbitrary Python.** The generic geoprocessing runner accepts any toolbox-qualified tool name and runs it with the user's GIS authority. That includes Python toolboxes (`.pyt`) and script tools, and tools that evaluate Python, such as Calculate Field or Calculate Value with a Python expression. Arbitrary Python is therefore reachable through `gp.run` even when the optional ArcPy runner is disabled. `gp.run` is confirmation-gated: in default mode it runs only after a person approves the request in the dockpane, and the approval is bound to the exact arguments. Read the tool name and the arguments preview before approving. In autonomous mode there is no approval, only the tier-based refusal above, which is metadata-driven and conservative but not a sandbox: a tool the catalog does not know is refused (fail closed), while a tool it classifies as Standard still runs with the user's authority; classification is metadata, not a sandbox. Use trusted toolbox names and disposable output paths, and do not expose this bridge to an untrusted client.
- Workflows reference registered operations and cannot embed a script step. This does not sandbox a geoprocessing tool's internals.
- Workflow operation allowlists are enforced when a workflow is saved and again when it runs. A workflow without `allowedOperations` may use any registered operation except those that execute user code (`gp.run`, `arcpy.run-script`). When `allowedOperations` is present it is exhaustive: every step's operation must be listed, and user-code operations must be listed explicitly. Violations are reported as the validation issue `operation_not_allowed`; `workflow_run` then fails with `invalid_workflow` before any step executes, including for a workflow file that was placed in the library directly without passing save validation. The allowlist names operation ids only and is not version-pinned: a listed id covers whatever version of that operation the running add-in registers, including a later version with different behaviour. Skill manifests must declare a non-empty `allowedOperations` or they are not loaded; a skill's list documents the operations its guidance relies on and is not a separate runtime gate.
- Workflows cannot execute confirmation-gated steps in default mode. `workflow_run` passes no approval token to its steps and there is no per-step approval yet, so a step such as `gp.run`, `metadata.update`, `feature.update`, `feature.delete`, `project.save` or `arcpy.run-script` fails with `confirmation_required`. In autonomous mode those steps run without review.
- Operation audit records are JSON lines in `%LOCALAPPDATA%\ArcGISProMCP\audit\operations.jsonl`. Each record has a `kind`: `operation` for every invocation, including rejected calls and unknown operation ids (logged with version `unknown` and error `operation_not_found`, id truncated to 256 characters), `dry-run` for every dry run, and `approval` for every local approve/deny decision, with `decision` (`approved`/`denied`) and `actor` (`panel-card` for a reviewed request, `panel-action` for a dockpane button). Operation records carry `autonomousBypass: true` when autonomous mode skipped review. Records store an argument hash, not the arguments. Approval expiry and `approval_cancel` are not audited. When the active file exceeds 16 MiB it is renamed to `operations.<utc-timestamp>.jsonl`; the newest five rotated files are kept and older ones deleted. All Pro processes append to the same file, so rotation is best effort: if another process holds the file or rotated it first, rotation is skipped and the record is still appended to the active file, which can then grow past the limit until a later rotation succeeds. Appends from several Pro processes are not coordinated, so simultaneous writes from two processes can interleave or overwrite each other's bytes; treat the log as best-effort evidence, not a tamper-proof record. An audit write failure does not hide an operation's known result; it adds an `audit_write_failed` notice.
- Captured images use opaque process-local handles, at most 5 MiB each. The host index retains at most 100 captures / 64 MiB, with a 24-hour TTL checked on access. Retention deletes only files owned by the current store, never arbitrary project files or historical demo exports. Physical deletion is best effort; orphan files from prior sessions or locked files are not automatically reclaimed. These are index bounds, not a cross-restart disk quota.
- GIS operation results can include source paths and project identifiers.
- Optional ArcPy execution is a trusted-local, arbitrary-code boundary. It is disabled unless explicitly configured, uses ArcGIS Pro's Python environment, and remains confirmation-gated with hash-pinned scripts plus bounded arguments, output, time, and working-directory controls. It is not an OS sandbox: an approved script has the signed-in user's file, network, ArcGIS, and licensing authority; deliberately detached child processes may outlive best-effort process-tree termination. See [ArcPy configuration](arcpy.md).

## Geoprocessing risk tiers

The add-in reads the installed system toolboxes' metadata (`Resources\ArcToolBox\toolboxes` next to `ArcGISPro.exe`, or `ARCGIS_PRO_MCP_TOOLBOX_ROOT`) without running any toolbox code, and classifies each tool. The first matching rule wins, in this order: (1) tool-level user code, meaning a script tool from a user (non-system) toolbox, or an unindexed `.pyt` or legacy binary `.tbx` toolbox, is UserCode; (2) Destructive; (3) a parameter that can select a Python expression makes the tool UserCode; (4) ConsumesCredits; (5) ReadOnlyQuery; (6) Standard. Because Destructive outranks expression-parameter UserCode, a tool such as `management.CalculateField` (declares `input_data_change` and accepts a Python expression) reports tier Destructive with `executesUserCode: true`. The table lists what each tier means for `gp.run`:

| Tier | Meaning | `gp.run` in default mode | `gp.run` in autonomous mode |
| --- | --- | --- | --- |
| **UserCode** | Python toolboxes (`.pyt`), non-system script tools and legacy binary `.tbx` toolboxes (rule 1), and non-Destructive tools with a parameter that can select a Python expression (rule 3). | Approval required; card says "Runs user code". | Refused without a token (`destructive_tool_requires_review`); runs with a person-issued approval token. |
| **Destructive** | Declares `input_data_change` or `edit_session`, or is on the curated list (`management.Delete`, `Rename`, `DeleteRows`, `DeleteFeatures`, `DeleteField`, `TruncateTable`, ...). | Approval required; card says "Modifies/deletes input data in place"; result carries `gp_mutates_input`. | Refused without a token (`destructive_tool_requires_review`); runs with a person-issued approval token. |
| **ConsumesCredits** | Declares `credits` (ArcGIS Online billable). | Approval required; card says "Consumes ArcGIS Online credits"; result carries `gp_consumes_credits`. | Runs, with the `autonomous_control` warning. |
| **ReadOnlyQuery** | Curated allowlist: `management.GetCount`, `management.GetRasterProperties`, `management.GetCellValue`. | Also runnable through `gp.query` without review. | Same. |
| **Standard** | Everything else: creates new outputs and does not declare in-place changes. | Approval required. | Runs, with the `autonomous_control` warning. |

- Classification is static metadata, not a guarantee. `no_data_change` is ignored (Delete carries it). System script tools are Esri-shipped Python and are reported, not refused. A curated destructive tool is Destructive even when the catalog has not indexed it (a missing or partial toolbox install), in either naming form (`management.Delete` or `Delete_management`, any case). Any other tool the catalog does not know (for example an imported toolbox alias) has an unknown tier: autonomous mode fails closed and refuses it with `destructive_tool_requires_review` (it could not be classified, so review is required); in default mode it still runs after approval and its result carries `gp_tool_not_indexed`.
- `gp.query` is ReadOnly: no revision, approval or autonomous mode is needed. It accepts only a plain `alias.ToolName` matching `^[a-z0-9]+\.[A-Za-z0-9]+$` that is on the allowlist and resolves to a system toolbox, so a user toolbox with the same alias cannot shadow it. Parameters are statically validated first, and the tool runs with outputs not added to the map, `overwriteoutput` false and no geoprocessing history.
- `gp.search` and `gp.describe` only read toolbox metadata.

The pipe supports at most eight concurrent requests (including the listener slot), with ten-second frame I/O timeouts. Host operations are serialized; discovery, state and approval calls bypass that gate. An `approval_status` call with `waitSeconds` holds one of those slots for its whole wait (up to 120 seconds), so the host lets at most two calls wait at once; any further waiting call returns the current status immediately with `waitNotice` set, and the client should poll again. That keeps at least five slots free for other requests. A stalled peer cannot monopolize the listener. ArcGIS itself may still delay state capture while its UI/MCT is busy. Each process defaults to a per-PID pipe; the gateway auto-selects one discovered live host or requires `ARCGIS_PRO_MCP_HOST_PID`/`ARCGIS_PRO_MCP_PIPE` when several are present. Reusing one explicit pipe across hosts is unsupported.

After request transmission starts, a dropped connection or response timeout is reported as `outcome_unknown`, not automatically retryable. The accepted write may still complete. Cancellation is cooperative; short SDK writes drain rather than detach from the executor. Disconnecting the panel blocks queued/new operations, not an already accepted write.

Workflows hold the same execution gate for their entire run, preventing registry/panel operations from interleaving between steps. They are still not atomic against external user edits or failures. Failed required dependencies are skipped and a run with any failed/skipped step is recorded as failed even when `continueOnError` allows independent steps to proceed. There is no automatic rollback. Audit/history persistence failures preserve the known result and return a warning rather than masking an accepted mutation.

Before production distribution: sign packages, complete live approval/replacement/shutdown tests, add crash-recoverable job status, and validate licensing/data policies. This bridge is a trusted-local-client boundary, not isolation between applications running as the same Windows user.
